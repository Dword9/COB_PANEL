## Идея (от юзера)

MuScriptor (нейросеть Kyutai × Mirelo) транскрибирует MP3 → MIDI,
разложенный по инструментам. MIDI и MP3 синхронны по абсолютным секундам.
Хотим: инструменты/роли из MIDI (барабаны, бас, гармония, соло) в реальном
времени превращать в сигналы для приборов — музыкально-реактивный свет
(кик → строб, бас → диммеры, соло → головы и т.п.), маппинг — визуально,
штатным графом нод Lumina.

## Часть 1. Источник MIDI: проект `N:\python_ide\music 2 midi`

### Что внутри

- Полная копия апстрим-репозитория MuScriptor в `muscriptor/` (пакет
  установлен editable в локальный venv).
- Модель `TranscriptionModel` (`muscriptor/muscriptor/transcription_model.py:247`),
  варианты small/medium/large = 103M/307M/**1.4B** параметров. Весы gated на
  HF, но уже скачаны в `N:\huggingface_cache` (`HF_HOME` в start_server.bat).
- Пайплайн: аудио → моно 16 кГц → mel-спектрограмма → LM генерирует
  MT3-подобные токены чанками по **5 сек** → события нот → MIDI (mido).
- venv: `N:\python_ide\music 2 midi\.venv` (Python 3.12, torch 2.6.0+cu124,
  fastapi, mido 1.3.3). GPU привязка: `CUDA_VISIBLE_DEVICES=GPU-4fb3...`
  = **RTX 4090** (RTX 5080 занята AI-инфрой, torch cu124 её не держит).
  Скорость: чанки 5 сек, на 4090 трек 3-4 мин ≈ десятки секунд.

### Формат выходного MIDI (критично для движка)

Генератор: `note_event2midi` (`muscriptor/muscriptor/tokenizer/notes.py:259-355`).

- **Type 1** (мультитрек), 480 ticks/beat, трек 0 — только set_tempo.
- **Темп фиктивный 120 BPM**, tempo-tracking НЕТ: ноты пишутся по
  **абсолютным секундам** на сетке 120 BPM → синк с MP3 просто по секундам.
- **Одна дорожка на инструмент** (track_name = имя группы: "clean electric
  guitar", "electric bass", "drums", "voice"...).
- **Каналы**: мелодические 0–8, потом 10–15; **drums = канал 9** (1-based 10).
- **Program number** = первый GM-пресет группы MT3_FULL_PLUS
  (`transcription_model.py:226-244`).
- **Velocity ВСЕГДА 100** — динамики нет (токенизатор её не восстанавливает).
  Нет pitch bend / CC.
- Постобработка: мин. длительность ноты 10 мс, обрезка перекрытий.

Проверено по `sample.mid`: type 1, 480 tpq, 71.8 сек, 5 треков:
guitar(ch0, prog26, 270 нот), bass(ch1, prog33, 268), drums(ch9, 649),
voice(ch2, prog52, 34).

Разделения по «стемам» как такового нет — дробление по распознанным
инструментам (типично 3–6 треков). Категории для DMX выводить самим из
канала (9=drums) и program. Можно ограничить набор инструментов параметром
`instruments` при транскрибации (`transcription_model.py:348-351`).

### Программный доступ (3 варианта)

1. **Штатный сервер пакета** (`python -m muscriptor serve`, тот же venv):
   `POST /transcribe/midi` — один блокирующий multipart POST → сразу байты
   .mid (`muscriptor/muscriptor/server.py:253-317`). Мьютекс (очередь),
   лимит 15 мин аудио. **Рекомендуемый для интеграции.**
2. Локальный `web_ui.py` (порт 8222, редактор MuScriptor): `POST /upload` →
   поллинг `GET /progress/{job_id}` → `GET /download/{job_id}` (3 вызова,
   без защиты от параллельных задач). Имеет `GET /midi_info/{job_id}` —
   разобранный MIDI в JSON (можно не писать JS-парсер!).
3. Прямой импорт `TranscriptionModel.transcribe_to_midi(path) -> bytes` —
   НЕ рекомендуется: 1.4B-модель + torch окажутся внутри DMX-процесса.

### Как играется MIDI+MP3 в MuScriptor (опыт синхронизации)

- Апстрим-фронт: Tone.js + SoundFont (spessasynth), offset через
  `getSecondsAtTime()` — `.seconds` даёт рассинхрон ~25 мс.
- Локальный редактор (web_ui.html): MIDI рендерится сервером в WAV-стемы,
  мастер-клок = `mp3Audio.currentTime`, подтяжка при дрейфе > 0.15 сек.
  Точность — десятки мс (нам за глаза, DMX-тик 16 мс).

## Часть 2. Lumina DMX: архитектура и что переиспользуем

### Общая схема

Сервер **тонкий** (`server_v4.py`, 614 строк): единственное состояние —
байтовый буфер 512 каналов. Вся логика в браузере: граф нод (React Flow) →
`graphEngine.ts` (~62 Гц) → WS `{ch,val}` → сервер → Art-Net (45 Гц) /
USB-крыло (30 Гц).

### Что уже есть (переиспользуем)

- **Точный аудио-транспорт**: `web/services/stemAudioManager.ts` — часы
  `AudioContext.currentTime`, play/pause/stop/seek, mute/solo, колбэки
  onTime, per-track анализаторы. Образец для транспорта шоу.
- **Анализ аудио**: `web/services/inputAudioManager.ts` — AnalyserNode,
  32 полосы → low/mid/high, Worker-тикер 16 мс (устойчив к фоновой вкладке).
- **MIDI-сервис**: `web/services/midiService.ts` — Web MIDI, state-map,
  learn-режим, инжект крыла. MIDI-нода как источник в графе уже работает.
- **Ноды**: InputNode (MP3/мик), AudioNode (DSP: gain/gate/attack/drop),
  StemNode (мультитрек WAV), MidiNode, FixtureNode, MathNode,
  GeneratorNode (LFO + tap-tempo BPM), PannerNode (бегущий свет),
  GroupActivatorNode, CombControllerNode (автономные расчёски).
- **Группы приборов**, конфликт-детектор каналов, автосейв в localStorage.

### Чего НЕТ

- Beat/onset-детекции (BPM только ручной tap-tempo у LFO).
- Таймлайна/секвенсора/«шоу»-режима вообще.
- Pub/sub состояния на сервере; сервер слепой (last-writer-wins).

### Точки расширения (file:line, проверено разведкой)

Новый тип ноды регистрируется в 5 местах:
1. `web/App.tsx:54-65` — `nodeTypes`;
2. `web/App.tsx:627-641` — дефолтные params в `addNode`;
3. `web/utils/graphEngine.ts:65` — порядок в `startOrder`;
4. `web/utils/graphEngine.ts:210` — новый `case` в switch движка;
5. `web/components/Sidebar.tsx:17-34` + `ContextMenu.tsx` — палитра.

Движок: `evaluateGraph()` (`graphEngine.ts:98-741`), тик из Worker 16 мс
(`App.tsx:588-600`), DMX пишут ноды fixture/panner/comb через dmxAggregator
(max-merge). Состояние нод — мутация `node.data.params` in-place (осознанный
хак, новые ноды делать так же, иначе рассинхрон с автосейвом).

### Ограничения (не наступать)

1. Канал 512 занят heartbeat-фликером (`App.tsx:553-556`). Один универс.
2. `audioConfigs`/`AudioReactiveConfig` в types.ts/constants.ts — МЁРТВЫЙ
   код, не строить на нём.
3. Потолок пути: движок 62 Гц → dmxClient 40 Гц (троттлинг 25 мс) → Art-Net
   45 Гц / крыло 30 Гц.
4. `midiService` игнорит velocity входящих (note→127/0); send шлёт во ВСЕ
   outputs.
5. Стемы — только WAV в память; blob-URL не переживает перезагрузку.
6. fftSize=256 — грубый анализ для музыки (для MIDI-пути не важно).
7. Движок мутирует params — см. выше про автосейв (дебаунс 500 мс).

## Часть 3. Дизайн фичи

### Нода «MIDI-трек» (рабочее имя: midi-track / NoteMap)

**Загрузка**: пара MP3 + .mid в ноду. Плеер — по образцу stemAudioManager:
AudioContext-clock, play/pause/stop/seek. MIDI-парсер: маленький JS-парсер
(npm `@tonejs/midi` или самописный по type-1 формату) — либо JSON через
`GET /midi_info/{job_id}` у web_ui.py (если MIDI пришёл из MuScriptor UI).

**Планировщик** (в case движка, каждый тик 62 Гц):
- читает транспортное время (секунды);
- индекс событий: указатель по отсортированным note-on/off (ноты уже по
  абс. секундам — прямое сравнение);
- активные ноты → огибающие 0..255: атака на note-on (мгновенно или ~10-30 мс),
  удержание, пока нота звучит, спад (release) ~150-300 мс после note-off;
  ударные — короткий фиксированный импульс (~100-150 мс, у них note-off
  почти сразу).

**Выходы по ролям** (классификация по каналу/program):
| Выход | Источник |
|---|---|
| `kick` | канал 9, ноты 35/36 |
| `snare` | канал 9, ноты 38/40 |
| `hats` | канал 9, ноты 42/44/46 |
| `bass` | program 32–39 |
| `harmony` | program 48–51 (струнные/пады), клавишные 0–7 опц. |
| `lead` | program 52–54 (voice) + соло-гитары 24–31 опц. |
| `all` | любая нота (энергия трека) |
Роли/правила — в params ноды (редактируемые диапазоны), дефолт как выше.

**Динамика без velocity** (у MuScriptor она всегда 100): уровень роли =
f(число активных нот, плотность за окно ~1 сек, высота pitch) — напр.
harmony с 4+ голосами ярче; kick всегда полный импульс.

**Маппинг на приборы — штатным графом**: выходы ноды → MathNode/AudioNode
→ входы FixtureNode/CombController/Panner. Это та же парадигма
«сцена = JSON графа», что и у ИИ-режиссёра (`docs/ai_event_director_concept.md`).

**UI ноды**: транспорт-бар (play/pause/stop, время), имя файлов, мини
пиано-ролл (canvas: треки-строки, ноты-черточки, курсор), светодиоды активности
ролей. Всё через renderRegistry (прямые DOM-апдейты, 60 fps, не через React).

### Фазы

1. **MVP**: нода с ручной загрузкой готовых файлов (транскрибация —
   в MuScriptor UI на :8222, как сейчас). Тест: sample.mp3 + sample.mid.
2. **Интеграция транскрибации**: из Lumina загрузка MP3 → server_v4
   проксирует в `muscriptor serve` `POST /transcribe/midi` → пара
   сохраняется в `media/` проекта, нода подхватывает по имени.
3. **Шоу-режим**: плейлист треков, квантование LFO/генераторов к часам
   транспорта, связка с ИИ-режиссёром.

### Открытые вопросы к реализации

- Точность мастер-клока: AudioContext.currentTime достаточна (опыт
  MuScriptor: дрейф медиа-элементов ~25-150 мс — для света ок).
- Где парсить MIDI: JS-парсер на фронте (независимость от web_ui.py) —
  предпочтительно; формат простой (type 1, секунды).
- Хранение файлов в проекте: сейчас blob-URL не переживает перезагрузку —
  для MVP терпимо (пере-загрузка файла руками), в фазе 2 — через media/.
- Одновременный LIVE-режим (inputAudioManager) и MIDI-режим — не конфликтуют
  (разные источники), но граф может хотеть мьютекс: решать в UI ноды.

## Часть 4. Дополнение 24.07: пианино-пиксель-движок (требования юзера)

Сценарий-эталон: фортепианная музыка (Nils Frahm и т.п.). Транскрибированный
MIDI от MuScriptor (точность проверена юзером — синхрон с MP3 хороший).
music2midi остаётся ОТДЕЛЬНЫМ проектом со своим UI (:8222) — звук MIDI там
не важен, играет всегда MP3; Lumina получает готовую пару файлов.

### Пиксель-карта расчёсок: 4 × 10 = 40 лучей

Ноты пианино → лучи напрямую (без ручной разводки графом — юзер не хочет
крутить ноды руками; дефолтный маппинг проектирует ИИ, юзер потом правит
подсказками):

- **Позиция**: pitch → x-координата луча на всех 40 пикселях (метафора
  клавиатуры: низкие слева, высокие справа). Диапазон — авто по файлу
  (min/max pitch) или фикс A0..C8.
- **Симметрия**: режим зеркальной пары (луч + отражение от центра) —
  одиночный луч смотрится криво, пара — красиво. on/off в params.
- **Ширина**: высокие ноты = 1 луч; низкие = размазанные 3–4 луча
  (гауссово/линейное распределение яркости по соседям).
- **Цвет**: градиент по высоте: низ = тёплые (amber/red), середина =
  насыщенные, верх = холодные → белые/синие, самые высокие — ярче/белее.
- **Яркость**: выше нота → ярче; низкие — темнее, но шире (компенсация
  площадью). Velocity у MuScriptor всегда 100 → вся динамика из pitch,
  ширины и плотности нот.
- **Огибающая**: атака ~10–30 мс на note-on, удержание пока звучит,
  release 150–300 мс; быстрые повторы одной зоны = перезапуск атаки
  (эффект «тык-тык-тык»).
- **Низы/бас**: низкие регистры (или bass-трек) → заливка COB на потолке
  цветом (тёплый, уровень от плотности). Остальные роли (kick/snare/…)
  — по таблице Части 3 через выходы ноды в граф.

### Архитектурное решение (важно)

Пиксель-движок встраиваем В САМУ ноду MIDI-трек: она рендерит 40-пиксельный
буфер и пишет каналы расчёсок напрямую через dmxAggregator (тот же путь,
что CombControllerNode; max-merge сам рассудит конфликты). Штатные выходы
ролей (kick/bass/lead/all) остаются для разводки на COB/прочее графом.
**CombControllerNode НЕ переписываем** — остаётся для автономного режима;
«кривое» панорамирование одним прибором на 4 расчёски заменяется родным
пиксель-маппингом новой ноды.

### Позиция расчёсок (рекомендация, решено с юзером 24.07)

Сейчас стоят на авансцене (передний край) — для пианино/акустики это спорно:
лучи бьют из переднего края прямо в зал/в глаза, глубины нет. Рекомендация:
**пол у задней стенки (задник), 2+2 по бокам от экрана**, лучи поверх зала;
наклон мотора ограничить, чтобы не заливать экран проекции. Свисток
беспроводной — переносятся вместе с ним, на репетиции сравнить обе позиции.
Для диско-формата авансцена тоже рабочая позиция (веер над толпой).

### Анализ реального файла (24.07, f653970….mid, 63 КБ)

825,5 с (13,7 мин), 8063 ноты, 5 инструментов. Ключевая находка —
**трек построен слоями, инструменты ВХОДЯТ по очереди**:
pad 0:00 (862 н.) → piano 1:35 (3101 н., pitch 27..94) → drums 7:20 (578)
→ guitar 9:55 (3257, «пулемёт» 170 мс) → bass 11:16 (265). Для шоу это
готовая драматургия: каждая новая роль = новый слой света, штатные
role-шины молчат до входа инструмента.
- Velocity = 100 ВЕЗДЕ (подтверждено по всем трекам) → динамика только
  через MP3-огибающую (см. ниже).
- Эхо-артефакт реален: повторы той же ноты <350 мс — piano 15,5%, pad 9%,
  drums 21,8%. Обработка в движке: повтор = перезапуск атаки с затуханием
  яркости ×~0,8 за повтор (сброс после паузы) — имитация затухающего эха.
- Аккорды до 4+ одновременных нот (IOI=0) — симметрия зеркалит кластеры.
- Dur: медиана 170 мс, но есть до 28 с (педаль/пад-тоны).

### Таймлайн инструментов (окна 30 с, тот же файл)

- **0:00–1:30** — synth pad соло (100%). Атмосфера.
- **1:30–10:00** — **PIANO СОЛО, 8 минут** (~100%, редкие вкрапления
  перкуссии с ~7:00: 6–15%). Основной пианино-акт для 40 лучей.
- **10:00–10:30** — переход: пианино уходит (58→0%), входит гитара.
- **10:30–11:30** — гитарный шторм: 689 нот/30 с (23 ноты/сек, tremolo).
- **11:30–конец** — полный бэнд: guitar 40–73% + drums 16–28% +
  bass 5–14% + pad до 20%. Кульминация ~12:30–13:00 (770 нот/30 с),
  спад на финале.
Вывод юзера подтвердился: «пианино» уходит из трека после 10-й минуты.
Движок НЕ привязываем жёстко к именам дорожек («гитара» с 23 нотами/сек —
вероятно не гитара вовсе; метки MuScriptor приблизительны). Маппинг по
РОЛЯМ: кто играет — тот и ведущий; дефолт роли = register+канал,
структура трека сама даёт драматургию (role-шины молчат до входа).

### Динамика из MP3 (идея юзера, 24.07 — принята)

Velocity нет, но MP3 синхронен → громкость берём из аудио:
- **Фаза 1**: оффлайн RMS-кривая MP3 (шаг ~10 мс) грузится парой к MIDI;
  уровень ноты = RMS на момент note-on. Дёшево, детерминировано.
- **Фаза 2**: спектральный уровень — STFT, амплитуда бина на основной
  частоте ноты = персональная громкость ноты даже в миксе инструментов.
- Рантайм-фолбэк: AnalyserNode на играющем MP3 (как inputAudioManager).

### Видео-вход (24.07)

Kimi K3 нативно понимает ВИДЕО (офиц. platform.kimi.ai, релиз 16.07.2026,
2.8T MoE, 1M ctx) — для оценки световой картинки можно слать клип, не

### Уточнения от 24.07 (вечер, обсуждение)

- **Эхо: отдельная логика НЕ нужна** (вывод юзера, верный). MIDI даёт
  отметки, MP3-огибающая даёт уровни — эхо в реальном аудио само затухает,
  значит уровень повтора придёт из MP3 уже пониженным. Эвристика «×0,8
  за повтор» отменяется; эхо-обработка = просто перезапуск атаки с
  уровнем из MP3.
- **Расчёски не должны молчать**, когда пианино уходит (после 10:00):
  приоритет-фолбэк источника пиксель-движка: piano → верхний мелодический
  голос (lead/guitar/synth/хоровые верха). Правило: пиксель-карта всегда
  играет самый высокий активный мелодический слой.
- **Концепт показа (юзер)**: демонстрация для детей под Nils Frahm —
  ПОЛНАЯ темнота + туман (хейзер). Главный экран НЕ используется
  (выжигает темноту). Два боковых проектора — абстракции под инструменты.
- **Видео-слой для 2 проекторов (новый трек работ, после MVP ноды)**:
  генеративные абстракции, синхронные с теми же role-шинами:
  плавные переливы (пад/струнные) → жидкостная/дымная симуляция, медленные
  флоу-поля; резкие удары (drums) → вспышки «молний в облаках»;
  pitch → оттенок, плотность → турбулентность. Два пути:
  (а) оффлайн-рендер клипов-петель под каждый акт + запуск из Resolume
  (через OSC-мост, этап 3); (б) реалтайм: WebGL-страница (fluid sim,
  fbm-дым, молнии) на весь экран проектора, питается шинами по WS от
  Lumina — проекторы и так висят на этом же ПК. Чёрный фон — контент
  в темноте должен жить в глубоком чёрном, иначе убьёт «полную темноту».

### План верификации анализа (24.07, решено с юзером)

Прежде чем светить на сцену — доказываем правильность на экране:
1. **В music2midi (web_ui :8222)**: кнопка «Спектральный анализ» у пары
   MP3+MIDI → сервер считает уровни нот (фаза 1: RMS на момент note-on;
   фаза 2: STFT-амплитуда на частоте ноты) → analysis JSON рядом с парой.
2. **Вкладка «Свет» там же**: canvas-визуализатор — 40 пикселей
   (4×10) псевдо-3D лучами вверх + КАЧАТЕЛЬ (MotorY: наклон от энергии/
   медленный LFO — атмосфера половину решает). Play → MP3 играет, лучи
   бегут. Так видим: синк, уровни, затухание эха, эстетику маппинга.
3. Пиксель-движок пишется ОДИН — рендерит буфер 4×10×RGBW; буфер идёт
   И в canvas (превью), И в DMX (через Lumina). Превью = честный
   WYSIWYG того, что будет на сцене.
4. Реальные приборы подключаем ПОСЛЕ отладки маппинга на визуализаторе
   (итераций много, в зал бегать долго). Потом — MIDI-нода в Lumina,
   тот же движок.

### Resolume Arena — заметка по ресурсам (24.07)

В простое жрёт ~15% CPU (Ryzen 9, 32 потока) и 15–20% GPU. Для
реактивного показа (2 проектора = генеративные WebGL-страницы) Арена
НЕ нужна: вывод напрямую fullscreen на дисплеи проекторов, без неё.
Арена остаётся для обычных шоу юзера. OSC-мост к ней — опционально,
если захочет гонять свои клипы внутри реактивного сетапа.

### Реализация MVP (24.07, ночь) — ЧТО СДЕЛАНО

**Этап 1 — анализ уровней (music2midi/web_ui.py):**
- `POST /analyze/{job_id}` → уровни каждой ноты из MP3: `lvl` (RMS на
  момент note-on) + `spec` (FFT-амплитуда на f0 + 0,35·2f0, окно 120 мс,
  12 кГц даунсэмпл — дешевле полного STFT). Нормировка по p95.
  `GET /analysis/{job_id}` → JSON (кэш на диске `web_ui_data/analysis/`).
- `_resolve_pair` ищет пару и на диске (переживает рестарт сервера).
- Замер: 8063 ноты за ~2 с. Эхо-повторы получают затухающие уровни
  из MP3 бесплатно (подтверждено на фрагменте).

**Этап 2 — вкладка «Свет» (music2midi/web_ui.html):**
- Пиксель-движок JS: 40 пикселей (4×10 RGBW), pitch→позиция/ширина/
  цвет/яркость, симметрия ×2, огибающая attack 20 мс/release (парам),
  качатель (sin 0,45 Гц × размах от энергии). Параметры: симметрия,
  ширина, спад, яркость, качатель, источник уровней (спектр/громкость),
  палитра (тепло→холод/радуга/моно-синий).
- Транспорт свой, аудио — штатный mp3Audio. Deep-link
  `/#light=<job_id>[,<seek_s>]` — автозагрузка пары + анализ + seek.
- Палитра thermal: hue 0,10→0,55 ВНИЗ (янтарь→красный→пурпур→синий) —
  в обход зелёной зоны; верхние ноты добеливаются W-каналом;
  gamma 0,72 поднимает тихие уровни.

**Грабли (не наступать):**
1. Курсор по нотам при seek: пропускать ноты нельзя — звучащие на t
   (start≤t<end+release) обязаны попасть в active, иначе после перемотки
   сцена пустая. (Первый баг: бары есть, лучей нет.)
2. Edge headless-скриншоты: `--headless=new --screenshot=...
   --virtual-time-budget=20000 --user-data-dir=<свежий каждый раз>`
   (кэш профиля отдаёт старую страницу — идентичные байты!). Яндекс-
   headless ВИСНЕТ — не использовать. Окно ≥1250px по вертикали,
   иначе низ canvas (приборы) за пределами кадра.
3. `decodeAudioData` в headless виснет — deep-link НЕ через loadResult,
   а свой лёгкий бут (switchTab + mp3Audio.src='/audio/jid' + runAnalysis).
4. Проверку рендера делать СВОИМИ глазами (читать PNG напрямую),
   VLM-прокси только как дубль.
5. DMX-прибор держит последнее значение ВЕЧНО — затухание обязан
   стримить отправитель. Из вкладки «Свет» шлём ПОЛНЫЙ кадр всех 164
   каналов расчёсок каждый тик (~30 Гц), дельта-пороги запрещены
   (баг «лучи не гаснут», 24.07). Конфликт last-writer-wins: Electron
   Lumina пишет те же каналы со своей частотой — для чистого теста
   выходить из неё через трей (крестик = прячет в трей, НЕ выход!).

**Этап 2,5 — DMX-выход и режимы (24.07, ночь, по отзыву юзера):**
- Кнопка **DMX** во вкладке «Свет»: WS → `ws://127.0.0.1:8000/ws`,
  шлёт пиксель-буфер массивом `{ch,val}` ~30 Гц (только дельты ≥4).
  Расчёски: база 250/293/336/379, каналы: MotorY=base (наклон из
  качателя, центр 128 ± 90), SpdY=base+1 (=80 при старте), пиксель i:
  R,G,B,W = base+2+i*4…5. При выключении — blackout + мотор в центр;
  blackout и на pagehide. Конфликт: десктоп Lumina (Electron) пишет те
  же каналы из своего графа — для чистого теста гасить её шоу.
- **Режим позиции**: «клавиатура» (pitch→x) / «бегунок» (walk: контур
  мелодии — выше → шаг вправо, шаг по величине интервала 1,5..7 px;
  аккорд dt<30 мс делит позицию; эхо-повтор — шаг 1,2 в ту же сторону;
  wrap по краям; цвет/ширина/яркость по-прежнему из pitch).
- **Диапазон**: «плотный» (p10..p90 высот — мелодия на всю строку,
  края = клэмп) / «полный» (min..max трека).
- Deep-link расширен: `#light=<job>[,<seek>[,<posMode>[,<range>]]]`.
- Ползунок **«направление»** (−100…+100): сдвиг базового угла качателя
  (в зал/на сцену), общий для превью и DMX-мотора.
- Ползунок **«гамма DMX»** (1,0–2,2, дефолт 1,4): выходная кривая —
  прижимает хвосты на дешёвом PWM приборов (чище гашение), ценой
  общей яркости (юзер принял).
- Родовой баг белого канала: CombControllerNode при снятии яркости
  нулит RGB, но не W — тот же класс «прибор держит последнее».
  Чинить при следующем заходе в CombControllerNode.
